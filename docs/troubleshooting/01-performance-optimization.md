# 性能优化：让 Excel 从“卡死”回到“秒回”

本篇讲 Excel 变慢的四个常见原因：易失性函数、全列引用、数组公式性能、百万行数据。每个原因先讲清原理，再给优化前后的公式对照与实测数据，最后给一套四步诊断流程。

- **所属栏目**：C16 错误排查与性能优化 ／ C16-L2-4 性能优化
- **适用版本**：Excel 2016／2019／2021／365（Windows 桌面版；百万行与数据模型部分需 64 位 Excel，Power Pivot 仅 Windows 版提供）
- **难度**：进阶
- **预计阅读时长**：35 分钟
- **更新日期**：2026-11-10

> **验证说明**：本篇实测数据为 LibreOffice headless 打开重算计时（方法与环境见 §5），不是 Excel 计时；易失性函数清单与每列最大行数 1,048,576 行的来源为 Microsoft 支持文档。**所有优化效果均未在 Excel 内执行验证**（无 Excel 环境），数字只代表本机实测的相对快慢，不作“在 Excel 里一定快多少倍”的承诺。

## 1. 学习目标

学完本篇，你将能够：

- 说出易失性函数的定义，并指出本表里哪些公式是易失性的
- 把 `A:A` 这类全列引用改成有界引用，并算出少扫多少个单元格
- 在 SUMPRODUCT 数组公式与 SUMIFS 之间选出更快的那一个，并说出为什么
- 对百万行数据选对处理方式：不用公式硬扛，改用 Power Query 或数据模型
- 按四步诊断流程定位一张慢表，先改最慢的一处

## 2. 基础概念

### 2.1 什么是重算

Excel 平时只重算受影响的公式：你改了 A1，只重算依赖 A1 的公式链。这叫智能重算。变慢通常不是公式本身难算，而是重算被触发得太频繁，或每次重算扫的范围太大。本篇四个原因正好各占一头：易失性函数是“触发太频繁”，全列引用是“扫得太多”，数组公式是“单次算得太重”，百万行是“数据本身太大”。

### 2.2 易失性函数：改一个格，全表重算

易失性函数（volatile function）每次工作表有任何改动都会重算，不管改动与它有没有关系。Microsoft 支持文档列出的易失性函数包括 `NOW()`、`TODAY()`、`RAND()`、`RANDBETWEEN()`、`OFFSET()`、`INDIRECT()`、`INFO()`、`CELL()`。一格 `=TODAY()` 本身不慢，可怕的是它会带着整条依赖链一起重算：一个易失性单元格后面跟了 100 个公式，改任意一格就等于重算这 101 个。

`OFFSET` 与 `INDIRECT` 还是“双重麻烦”：它们除了易失，还挡住智能重算的优化——Excel 看不清它们到底引用了哪些格，只能按最保守的方式处理。

### 2.3 全列引用：5 万行数据，扫 104 万行

Excel 每列最多 1,048,576 行（Microsoft 支持文档）。写 `=SUMIF(A:A, "电脑", B:B)` 时，Excel 要对整列 1,048,576 个单元格做判断，哪怕你的数据只有 5 万行：多扫约 100 万个空单元格。改成 `=SUMIF($A$2:$A$50001, "电脑", $B$2:$B$50001)`，只扫 5 万行，少扫约 95.23% 的单元格（1,048,576 − 50,000 = 998,576 个；998,576 ÷ 1,048,576 ≈ 0.9523）。数据只有 1,000 行时差距更大：全列是 1,048,576 个单元格，有界是 1,000 个，相差约 1,049 倍。

### 2.4 数组公式性能：能不用数组，就不用数组

`SUMPRODUCT((条件)*(数值))` 是数组运算：先把两个区域逐个相乘得到中间数组，再求和。`SUMIFS` 是内置的条件求和，走专门优化过的路径。同样的条件求和，`SUMIFS` 通常更快；只有 `SUMIFS` 写不出的条件（如“数量 × 单价再求和”这种逐行相乘）才需要 `SUMPRODUCT`。动态数组函数（`FILTER`、`SORT`、`UNIQUE`，仅 365/2021+）溢出的是结果，不是逐格公式，比旧式 CSE 数组公式轻。

### 2.5 百万行数据：公式扛不住，换工具

一百万行 × 几列的表，公式再优化也快不起来：每次重算都要扫全表，文件也大。正确分工是：Power Query 负责清洗与合并（只在刷新时算一次），数据模型（Power Pivot）负责汇总（列式压缩，百万行是它的主场），工作表公式只负责展示少量结果。32 位 Excel 内存上限低，百万行务必用 64 位。

## 3. 操作步骤

1. 先定位：打开慢表，按 `Ctrl + End` 看实际已用区域是不是远大于数据区（多了很多空行空列也会拖慢）；再用「公式 → 公式求值」或逐段删公式试，看哪一块最慢。
2. 改全列引用：把 `A:A`、`B:B`、`1:1` 这类整列/整行引用改成有界引用（`$A$2:$A$50001`），用 `Ctrl + End` 确认的最后一行定下界。
3. 换易失性函数：`TODAY()` / `NOW()` 只在确实需要“每天变”的地方保留，其余改成手填的静态日期；`OFFSET` 改 `INDEX`（`INDEX(A:A, 行号)` 不易失），`INDIRECT` 改直接引用或 `CHOOSE`。
4. 数组公式改 SUMIFS：凡是 `SUMPRODUCT((条件)*(数值))` 能写成 `SUMIFS` 的，一律改写；只保留 `SUMIFS` 写不出的逐行相乘。
5. 百万行上模型：数据超过 20 万行就不要再往工作表里堆公式，先导进 Power Query 清洗，再进数据模型写度量值，工作表只放结果。
6. 收尾设置：把计算选项切到「手动」（公式 → 计算选项 → 手动），改完按 `F9` 一次算完；批量写代码时用 VBA 关掉 `ScreenUpdating` 与 `Calculation`（见 C11 02 篇 §2.2）。

## 4. 图文示例

一张 5 万行销售表（类别、数量、单价三列），优化前：汇总区有 20 个 `=SUMIF(A:A, "电脑", B:B)` 全列公式，另有 5,000 个 `=RAND()` 做抽查编号；每次改一格都要卡一下。优化后：20 个公式改成有界引用 `=SUMIF($A$2:$A$50001, "电脑", $B$2:$B$50001)`，5,000 个 `RAND()` 改成一次性生成的静态随机数（复制 → 选择性粘贴为值）。结果：汇总公式只扫 5 万行，随机数列固定后不再每次改动都重算；打开时间的实测对比见 §5——本次测量中全列与有界的打开耗时没有显著差别，收益主要在每次改数时（机制见 §2.2、§2.3），不要只看打开时间。 ![优化前后对照](images/u12-troubleshooting-01-performance-optimization-01.png)

## 5. 公式和代码

### 5.1 优化前后对照

```excel
' 全列引用 -> 有界引用
=SUMIF(A:A, "电脑", B:B) ' 优化前: 扫 1,048,576 行
=SUMIF($A$2:$A$50001, "电脑", $B$2:$B$50001) ' 优化后: 只扫 50,000 行

' 数组公式 -> SUMIFS（同一任务：电脑类总数量）
=SUMPRODUCT((A2:A50001="电脑")*(B2:B50001)) ' 优化前: 数组运算，逐行相乘再求和
=SUMIFS(B2:B50001, A2:A50001, "电脑") ' 优化后: 内置条件求和，同一结果 105,045

' 只有 SUMPRODUCT 能写的任务（数量 × 单价再求和），不要硬改 SUMIFS
=SUMPRODUCT((A2:A50001="电脑")*(B2:B50001)*(C2:C50001)) ' 电脑类金额合计 119,488,800

' 易失性 OFFSET -> INDEX
=OFFSET($A$1, 行号-1, 0) ' 优化前: 易失, 每次改动都重算
=INDEX($A:$A, 行号) ' 优化后: 不易失, 只在依赖变化时重算

' 易失性 RAND() -> 静态值
=RAND() ' 优化前: 每次改动都出新随机数
' 优化后: 在一列写 =RAND(), 复制整列 -> 右键 -> 选择性粘贴 -> 值, 随机数就固定下来
```

运行结果：优化前后公式算出的结果值相同：同一份 5 万行数据上，SUMIF 全列与有界均为 105,045，SUMPRODUCT 与 SUMIFS（电脑类总数量）均为 105,045（Python 对原数据独立重算；LibreOffice 打开重算的 bounded.xlsx E2 也是 105,045）。差别只在重算时间，不在结果。

### 5.2 实测对比数据（LibreOffice headless 打开重算计时）

| 对比组 | 改前（中位数） | 改后（中位数） | 3 次测量范围 |
|---|---|---|---|
| 全列 SUMIF（20 个公式） | 2.49 秒 | 有界 SUMIF 2.96 秒 | 全列 2.46–2.61 秒；有界 2.46–5.08 秒 |
| SUMPRODUCT（10 个公式） | 5.50 秒 | SUMIFS 4.28 秒 | SUMPRODUCT 3.96–7.62 秒；SUMIFS 3.93–4.35 秒 |
| RAND() 5,000 个 + 求和 | 1.51 秒 | 静态值 + 求和 1.32 秒 | 易失 1.43–1.64 秒；静态 1.30–1.44 秒 |
| 2 万行 SUMIFS | 2.49 秒 | 20 万行 SUMIFS 6.32 秒 | 2 万行 1.93–2.60 秒；20 万行 6.08–6.33 秒 |

环境：LibreOffice 24.2.7.2 headless，同一台机器，5 万行随机销售数据（类别 5 种、数量 1–20、单价 100/300/800/1500/3000）；每个文件测 3 次取中位数；计时含打开、重算、转存全过程。

实测方法：本机 LibreOffice 无界面打开含公式的工作簿并转存，公式在打开时重算；每个文件测 3 次取中位数。工作簿用 openpyxl 生成，公式无缓存值，打开即全量重算；数据为 5 万行随机销售数据（类别 5 种、数量 1–20、单价 100/300/800/1500/3000）。本实测只说明相对快慢：同一台机器、同一批数据、改前改后的对比；换 Excel、换机器、换数据量，绝对时间会变。注意：打开、加载与保存的固定开销（约 2–3 秒）占主导，单次测量波动可达 2 倍（有界组 2.46–5.08 秒），因此本表只能定性看方向，不能读出精确的加速倍数；下文结论按这个口径写，凡是“算出来的”（单元格数）与“测出来的”（计时）严格分开。

实测结论（与 §2 原理一致）：

- 全列 vs 有界：本次测量未测出差别——有界中位数 2.96 秒反而高于全列 2.49 秒，3 次波动（2.46–5.08 秒）超过两者差异。全列更慢的依据是扫的单元格数（1,048,576 − 50,000 = 998,576 个空单元格，算出来的），不是这次计时；不要把“全列一定慢 X 倍”说成实测结论。收益主要在每次改数时只重算 5 万行依赖链，不在打开那一下。
- SUMPRODUCT vs SUMIFS：中位数 5.50 秒 vs 4.28 秒，SUMIFS 快约 22%（5.50 ÷ 4.28 ≈ 1.29），但 SUMPRODUCT 3 次波动 3.96–7.62 秒，与 SUMIFS 的 3.93–4.35 秒有重叠，只能定性说 SUMIFS 不慢于 SUMPRODUCT。
- 易失性函数的代价不在单次打开，而在每次编辑：`RAND()` 列在打开时只算一次，1.51 秒 vs 静态值列 1.32 秒，只慢约 14%（1.51 ÷ 1.32 ≈ 1.14）；真正的差别是改任意一格时易失性列会带着依赖链重算，静态值列不会。本表“打开重算”一项测不出这个差别，特此说明，不把打开时间说成全部代价。
- 百万行不要只看公式：20 万行 6.32 秒 vs 2 万行 2.49 秒，约 2.5 倍（6.32 ÷ 2.49 ≈ 2.54），不是一个数量级；行数 ×10、时间 ×2.5，说明单公式的规模增长是次线性的，但绝对时间仍在涨；超过 20 万行就按 §3 第 5 步上 Power Query 与数据模型。

## 6. 实际工作场景

### 场景 1：月度报表打开要 30 秒

财务每月打开一张汇总表要等 30 秒，改一个数又要等。做法：按 §3 诊断，先发现汇总区 20 个 `SUMIF(A:A,...)` 全列公式与一列 `TODAY()`；把全列改成有界引用，`TODAY()` 改成每月 1 号手填的静态日期（报表日期本来就每月只变一次）。结果：汇总公式只扫实际行数，改数只重算依赖链，不再每次全表重算；打开时间的实测对比见 §5（本次测量未测出全列与有界的打开耗时差别，收益主要在改数时）。报表日期改由人工每月填一次，代价是每月多一个动作。

### 场景 2：百万行对账，公式直接卡死

两张各 100 万行的对账表要在 Excel 里按单号匹配金额，VLOOKUP 全列引用直接卡死。做法：不写公式，Power Query 里按单号合并查询（只在刷新时算一次），结果进数据模型，工作表只放汇总结果。结果：刷新一次几分钟跑完，之后打开秒开；代价是流程从“写公式”变成“点刷新”，需要接受一次学习成本。

## 7. 常见错误

| 错误现象 | 原因 | 解决方案 |
|---|---|---|
| 把 `A:A` 改成有界引用后，新增的行没算进去 | 下界写死了（如 `$A$50001`），新增到 50002 行的行不在范围内 | 下界留余量（如按 `Ctrl + End` 的最后一行再加 1000 行），或把数据区转成超级表（结构化引用自动扩展，见 C02-L2-5） |
| `OFFSET` 改 `INDEX` 后结果不对 | `OFFSET(起点, 0, 0)` 与 `INDEX(列, 行号)` 的行号基准不同（OFFSET 是偏移量，INDEX 是绝对行号） | `OFFSET($A$1, n-1, 0)` 对应 `INDEX($A:$A, n)`，注意减 1 |
| `RAND()` 粘贴成值后，下次打开数字不变了 | 选择性粘贴为值就是把随机数固定下来，这是优化的目的 | 需要每次都变时不要粘贴成值，改成只在需要时按 `F9` 重算，或把随机数生成移到 VBA 里按需跑一次 |
| 计算选项改成手动后，公式结果一直是旧数 | 手动模式下改数据不会自动重算 | 改完按 `F9` 全量重算；发给别人前先切回自动，或在表头注明“本表为手动计算，改数后按 F9” |
| SUMPRODUCT 改 SUMIFS 后结果变了 | 两者语义不同：SUMPRODUCT 是逐行相乘再求和，SUMIFS 是按条件求和；只有“按条件求和”能直接改写 | 需求是“数量 × 单价再求和”时保留 SUMPRODUCT，改写前先对一小段数据逐格验算 |
| 百万行表转了超级表还是卡 | 超级表只是结构化引用，不解决重算量；百万行公式该慢还是慢 | 按 §3 第 5 步上 Power Query 与数据模型，不要只换引用写法 |
| 关了屏幕刷新后 Excel 界面不动了 | VBA 里关了 `ScreenUpdating`，过程出错提前退出，没恢复 | 在错误处理段里恢复开关（见 C11 05 篇 §4.4 集中处理写法）；救急可在立即窗口执行 `Application.ScreenUpdating = True` |
